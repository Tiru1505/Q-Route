# Integration guide — engine ↔ backend ↔ frontend

For whoever is writing the FastAPI layer.

**The short version:** the optimisation engine already returns the exact JSON
the React frontend expects. Your job is to expose it over HTTP. No field
renaming, no reshaping — if you find yourself translating, something has gone
wrong and it is worth a five-minute conversation instead.

---

## The one rule that matters

```python
from engine import get_engine

engine = get_engine()      # ~30 s: loads a 286,603-node graph. ONCE, at startup.
```

Loading the graph takes about 30 seconds. **Never construct the engine inside a
request handler.** Build it during FastAPI's startup event and hold it for the
process lifetime. `get_engine()` is a singleton, so calling it repeatedly is
safe — but the first call is the slow one.

The engine is stateful: it remembers the current traffic scenario, the active
trip, and the alert history. That is intentional — rerouting is meaningless
without knowing where the driver is. For a single-user demo this is fine. For
multiple concurrent users you would key one engine per session, but that is not
needed for SIH.

---

## Endpoint map

Every method already returns a JSON-serialisable dict. Wire them straight
through.

| Frontend call | Suggested endpoint | Engine method |
|---|---|---|
| `getHealth()` | `GET /health` | `engine.health()` |
| *(dropdowns)* | `GET /places` | `engine.places()` |
| *(selector)* | `GET /scenarios` | `engine.scenarios()` |
| *(selector)* | `GET /modes` | `engine.modes()` |
| `getRouteOptimization()` | `POST /optimize-route` | `engine.plan(start, end, algorithm, mode)` |
| `getAlternativeRoutes()` | — | already in `plan()`'s `routes[1:]` |
| `getTrafficData()` | `GET /traffic` | `engine.traffic()` |
| `reroute()` | `POST /reroute` | `engine.check_reroute()` |
| `getAlerts()` | `GET /alerts` | `engine.alert_history()` |
| `getBenchmark()` | `GET /benchmark` | `engine.benchmark(stops, trials)` |
| `getConvergence()` | `GET /convergence` | `engine.convergence()` |
| `getScalability()` | `GET /scalability` | `engine.scalability()` |
| *(demo control)* | `POST /scenario` | `engine.set_scenario(name)` |
| *(demo control)* | `POST /advance` | `engine.advance(fraction)` |
| *(demo control)* | `POST /spike` | `engine.spike_route(level)` |
| *(demo control)* | `POST /accept` | `engine.accept_reroute()` |
| *(multi-stop)* | `POST /multistop` | `engine.plan_multistop(depot, stops)` |

Minimal example:

```python
from fastapi import FastAPI
from engine import get_engine

app = FastAPI()
engine = None

@app.on_event("startup")
def startup():
    global engine
    engine = get_engine()          # slow, once

@app.post("/optimize-route")
def optimize(body: dict):
    return engine.plan(
        body["start"], body["end"],
        algorithm=body.get("algorithm", "qpso"),
        mode=body.get("mode", "balanced"),
    )
```

## Response shapes

### `plan()` → `POST /optimize-route`

```json
{
  "routes": [
    {
      "id": "r1", "label": "Route 1", "algorithm": "QPSO",
      "recommended": true, "fastest": true,
      "distanceKm": 18.75, "etaMin": 24.7, "congestion": 0.206,
      "score": 96, "timeSavedMin": 7.2,
      "via": "Jubilee Hills → Banjara Hills → Mehdipatnam",
      "color": "#10b981", "avgSpeedKph": 45.5, "hops": 233,
      "path": [[17.4435, 78.3772], [17.44, 78.39], "..."]
    }
  ],
  "recommended": { "...same object..." },
  "meta": {
    "from": "Hitec City", "to": "Charminar", "mode": "balanced",
    "solverUsed": "Dijkstra (provably optimal for single-pair)",
    "computeMs": 3655.0
  }
}
```

`path` is `[[lat, lon], ...]` — Leaflet's order, ready for `<Polyline positions=…>`.

### `check_reroute()` → `POST /reroute`

```json
{
  "shouldReroute": true,
  "reason": "congestion ahead: remaining journey is +230% off plan",
  "currentEtaMin": 45.6, "newEtaMin": 16.2,
  "timeSavedMin": 29.4, "savedPct": 64.4,
  "blocked": false, "computeMs": 517.0, "algorithm": "Dijkstra",
  "alert": {
    "kind": "reroute", "severity": "severe",
    "title": "Faster route available",
    "message": "Heavy congestion detected …",
    "action": "Switch route",
    "currentEtaMin": 45.6, "newEtaMin": 16.2,
    "timeSavedMin": 29.4, "savedPct": 64.4
  },
  "suppressedBecause": null,
  "newRoute": { "...route object..." }
}
```

`alert` is `null` when the engine deliberately stays silent — then
`suppressedBecause` explains why. **Show that in the UI.** The suppression
logic is a feature, not a failure, and it is worth demonstrating to judges.

### `traffic()` → `GET /traffic`

```json
{
  "segments": [
    { "id": "123_456_0", "name": "Panjagutta Flyover", "level": "severe",
      "congestion": 0.94, "color": "#ef4444", "speedKph": 8.2,
      "path": [[17.4256, 78.45], [17.418, 78.456]] }
  ],
  "incidents": [
    { "id": "inc0", "type": "accident", "location": "Mehdipatnam",
      "coords": [17.395, 78.436], "severity": "severe" }
  ],
  "scenario": "peak_hour"
}
```

Capped at 400 segments by default — 741,203 edges will not fit down a wire or
render on a map. Raise via `engine.traffic(limit=…)` if needed.

## Switching the frontend off mock data

One environment variable:

```bash
VITE_USE_MOCK=false
VITE_API_BASE=http://127.0.0.1:8000
```

Vite already proxies `/api` → `127.0.0.1:8000` in dev, so CORS is a non-issue
locally. `src/services/api.js` needs no code change — it already branches on
that flag.

---

## Two things to get right

**1. Do not rename fields.** The engine emits camelCase specifically to match
`frontend/src/data/mockData.js`. If the API renames anything, both sides need
changing and the mock/live paths diverge.

**2. Keep the honest labels.** `meta.solverUsed` says Dijkstra is used for
single-pair routing, because it is provably optimal there and QPSO cannot beat
it. Do not relabel that as QPSO in the API. QPSO's genuine win is the
multi-stop endpoint, where Dijkstra cannot solve the problem at all — that is
the claim worth making, and it holds up under questioning.

## Verifying the whole chain

```bash
python backend/scripts/run_demo.py
```

Runs all eight demo steps through the same `QROEngine` the API will use. If
that passes, the engine is sound and any remaining problem is in the HTTP
layer.
